Integración de Servicio de Notificaciones Push

Caso de Estudio: Aplicación Móvil de Seguimiento de Solicitudes de Servicio Técnico. Solución integral de comunicación asíncrona nube-dispositivo para eliminar el sondeo manual (polling).

📡 Entregable 4: Identificación del Servicio Utilizado y Mecanismo
Arquitectura de Comunicación

Problema planteado: ¿Cómo puede una aplicación móvil recibir información de un servicio en la nube sin que el usuario tenga que consultar manualmente la aplicación?

Solución: Se implementó el servicio Expo Push Notifications Service Gateway trabajando en conjunto con Firebase Cloud Messaging (FCM en Android) y Apple Push Notification service (APNs en iOS). En lugar de que el dispositivo móvil mantenga peticiones cíclicas por HTTP (sondeo/polling) que agotan la batería y el plan de datos, el sistema operativo mantiene un único canal de socket TCP persistente de bajo consumo energético con los servidores de Google/Apple. Cuando ocurre un cambio de estado en el backend, se dispara una notificación push unidireccional hacia dicho canal.

🔑 Entregable 5: Explicación de la Función del Token de Notificaciones
Identificador de Suscripción

¿Qué es un Token Push?

Es una cadena alfanumérica única y efímera generada criptográficamente por la plataforma de notificaciones (Expo / Google FCM / Apple APNs) cuando el usuario autoriza los permisos de notificación.

ExponentPushToken[xG_48z0YcI...]

¿Cuál es su Función Técnica?

  • Direccionamiento en la Nube: Permite al servidor saber con exactitud a qué dispositivo físico remitir el mensaje sin conocer su dirección IP fija (la cual cambia constantemente entre Wi-Fi y redes móviles 4G/5G).
  • Desacoplamiento: Traspasa routers, firewalls y NATs sin requerir abrir puertos en el móvil.
  • Seguridad y Revocación: Si el usuario desinstala la app o revoca permisos, el token se invalida automáticamente.

Comportamiento al seleccionar la notificación (Parte 2.5):

Cuando el usuario presiona la notificación en la bandeja del sistema operativo, el listener Notifications.addNotificationResponseReceivedListener intercepta el evento, extrae la propiedad data.requestId del payload y redirecciona automáticamente a la vista modal detallada de la solicitud (#SOL-1041), actualizando la línea de tiempo en pantalla sin requerir recargar la aplicación ni navegar manualmente.

Comportamiento cuando NO se han concedido los permisos (Parte 4.5):

Si el usuario deniega los permisos de notificación, el método registerForPushNotificationsAsync() devuelve { success: false, permissionStatus: 'denied' }. La aplicación muestra un banner rojo de advertencia, inhabilita el token para no saturar el servidor con intentos fallidos, y ofrece un botón interactivo que guía al usuario a activar los permisos desde los Ajustes del sistema.

🔒 Entregable 6: Descripción de Medidas de Seguridad Implementadas
Seguridad y Ciberdefensa
  • ✓
    Cifrado en Tránsito TLS 1.3 / HTTPS
    Toda comunicación entre el backend remoto, el Gateway de Expo y el dispositivo móvil viaja cifrada mediante canales seguros end-to-end con certificados X.509 validados.
  • ✓
    Expo Push Access Tokens (Autenticación)
    Se implementa soporte para tokens de acceso secretos emitidos por EAS (Expo Application Services) en los encabezados HTTP Authorization: Bearer <TOKEN> para prevenir spoofing.
  • ✓
    Minimización de Datos y Privacidad (PII)
    Los payloads de las notificaciones únicamente transportan identificadores referenciales (requestId, status), evitando enviar contraseñas o datos financieros en el texto push.
  • ✓
    Validación Estricta de Esquemas de Payload
    Tanto el backend emisor como el receptor móvil validan los tipos de datos y sanitizan strings para prevenir inyecciones o desbordamientos de buffer en la barra del SO.
